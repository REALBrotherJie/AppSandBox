# 04 包解析、签名与网络（阶段 2、4、9、14）

## PackageParser 版本适配（阶段 2）

沙箱自己解析 apk，必须跟上 AOSP `PackageParser` 的版本变化：

- **API 28+ (Pie)**：`collectCertificates` 签名变为 `(Package, boolean)`，签名数据移入 `mSigningDetails`。
- **API 33+ (Tiramisu)**：引入 `FrameworkPackageUserState`，构造/字段布局又变。
- 处理办法：为每个断代做一层 mirror（反射封装），`PackageParserCompat` 按 `SDK_INT` 走对应分支，
  并统一提供 `getSignatures()`。

**hidden API 解封**：Android 9+ 封锁了对非 SDK 接口的反射，mirror 反射层会失败。
引入 `hiddenapibypass`，在核心启动时解除封锁。注意：某些 ROM（本机 Mi10）连 `setHiddenApiExemptions` 本身都失败，
不能假设一定能解封。

## signingInfo：现代签名校验读的是它，不是 signatures（阶段 14）

**通用平台事实**：Android 9+ 的签名校验（GMS `GoogleSignatureVerifier`、以及很多 app 自带的防篡改）
请求 `GET_SIGNING_CERTIFICATES` 并读 `PackageInfo.signingInfo`，**不再读**已废弃的 `signatures` 数组。

- 旧沙箱只填 `pi.signatures`（对应 `GET_SIGNATURES`），未填 `pi.signingInfo` → 校验方拿到 null →
  "package info is not set correctly" → 判定签名无效。
- **解决**：`generatePackageInfo` 在 `SDK>=28` 且请求 `GET_SIGNING_CERTIFICATES` 时，
  用已采集的签名通过反射构造 `SigningInfo` 填入。要兼容 `SigningDetails` 的类迁移：
  - Android 13+：`android.content.pm.SigningDetails`
  - 之前：`android.content.pm.PackageParser$SigningDetails`
  - 构造 `SigningDetails(Signature[], int signatureSchemeVersion)`（version=1 即 JAR 签名，足够做证书比对），
    再 `new SigningInfo(SigningDetails)`。
- 这是**通用改进**，利好所有做 `GET_SIGNING_CERTIFICATES` 校验的 app。

## 动态广播权限（阶段 4）

**通用平台事实**：真实 PackageManager 会为每个包**自动定义并授予**一个自限权限
`<pkg>.DYNAMIC_RECEIVER_NOT_EXPORTED_PERMISSION`（Android 12+）。
AndroidX 的 `ContextCompat.registerReceiver` 会用 `checkSelfPermission` 校验它。

- 沙箱自己解析包、从没定义过这个权限 → 所有用 AndroidX 注册广播的 app 启动即崩。
- **解决**：解析时把该权限补进 `requestedPermissions`，并在权限检查（AM 代理与服务端）对该后缀直接返回"已授予"。

## 明文流量 / Network Security Config（阶段 9）

**通用平台事实（重要）**：平台**按进程**只从**宿主包**构建一份 network-security policy，
guest **继承宿主策略**，guest 自己清单里的 `networkSecurityConfig` / `usesCleartextTraffic` 在沙箱内**不生效**。

- 症状：guest（如酷安）走 `http://` 明文的头像/图片被 `CLEARTEXT communication not permitted` 拒
  （因为宿主 targetSdk 高、默认禁明文）；走 https 的首图能显示，掩盖了问题。
- **走不通的路**：运行时替换 `libcore.net.NetworkSecurityPolicy` 实例——该类在 apex core-libart 里，
  `getDeclaredFields()` 返回空、无 `setInstance`，hidden-API 过滤连 meta-reflection 都挡住。**运行时改 libcore 策略此路不通。**
- **可靠方案（宿主级）**：给宿主清单 `<application>` 加 `usesCleartextTraffic="true"` +
  `networkSecurityConfig="@xml/network_security_config"`（`base-config cleartextTrafficPermitted="true"`，
  trust-anchors 含 system+user）。宿主放开明文 → 每个 guest 进程按宿主清单建策略，自动继承。
- **配套**：`makeApplication` 前要清空已装载的 network security config（置空 `ApplicationConfig.sInstance`），
  否则宿主+guest 规则合并抛 `Found multiple conflicting per-domain rules`，导致 `makeApplication` 返回 null → onCreate NPE。

**结论**：宿主放开明文是沙箱宿主的通行做法（guest 的 NSC 在沙箱内本就不生效，统一继承宿主）。
若将来要按 guest 精确套用其 NSC，需要可写的 per-process 策略（本 ROM 不可行）。

## splitSourceDirs 陷阱（阶段 2/4）

克隆的 app 是单 `base.apk`、无 config split。Android 9+ 的 `LoadedApk.registerAppInfoToArt()` 会
**同步遍历** `splitSourceDirs` 并按 `splitNames` 索引，若伪造 split 而无对应 `splitNames` 条目 →
`read from null array` 崩溃。**不要伪造 split，把 split 数组置空。**

## 给 AppSandBox 的启示

- 若做包解析，从一开始就为 `signingInfo`（`GET_SIGNING_CERTIFICATES`）留位置，而不是只填 `signatures`。
- 明文/NSC 属于**宿主级配置**，在宿主清单里解决，别指望运行时改 libcore。
- 每个"真实 PMS 会自动注入"的东西（如 `DYNAMIC_RECEIVER_NOT_EXPORTED_PERMISSION`），
  自解析包时都要显式补上，否则现代 AndroidX 校验会崩。
