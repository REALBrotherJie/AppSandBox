# 05 反检测与路径隐藏（阶段 5、6、8、10）

> ⚠️ 反检测明确属于 AppSandBox clean-room 阶段**排除**的能力（见 `docs/CLEAN_ROOM.md`）。
> 本文仅作为"若将来进入运行时/对抗阶段会遇到什么、边界在哪"的前瞻记录，不作为当前实现指引。

## 量化标尺：先有度量再谈反检测

做了一个 `vadetect` 探针 app：枚举暴露沙箱的信号，每项报 `LEAK` / `clean`，
以**泄露总数**作为反检测的量化指标。用它在沙箱内外对比，能立刻定位缺口，也能防回归。
检测项覆盖：dataDir/filesDir、sourceDir/nativeLibDir、`/proc/self/{maps,mounts,cmdline,comm}`、
VA 类是否可见、已安装应用数、同包名多进程、uid 一致性、installer。

**启示**：任何"隐藏"能力都要先有可复现的度量，否则无法判断是否真的干净、是否回归。

## 反检测的根本依赖：native IO 重定向必须先真正生效

dataDir / filesDir / sourceDir / proc maps / mounts 这些**路径级泄露**，
全都要靠 native IO 重定向"把干净的假路径映射回真实存储"才能修，
而重定向依赖 arm64 inline hook（见 [02](./02-arm64-inline-hook与IO重定向.md)）。

> **在 arm64 inline hook 修好之前，路径级反检测无法安全落地。**
> 试过让 dataDir 直接报干净路径，结果 file-io 直接 ENOENT，拖垮每一个 app，已回退。

这是顺序约束：**先有能工作的重定向，才能报告干净路径**。

## 逐项消除与踩坑

1. **已安装应用数**：`getInstalledApplications`/`getInstalledPackages` 合并宿主的系统应用，
   数量从个位数（只有沙箱内几个）变成几百个，像真机而非沙箱。这项不依赖 native hook，可先做。

2. **dataDir / filesDir**：解析时报告干净的 `/data/user/0/<pkg>` / `/data/user_de/0/<pkg>`，
   native 重定向把这些干净路径映射回真实 per-user 存储。**报告干净路径与重定向必须成对出现**，
   否则文件访问 ENOENT。

3. **sourceDir / nativeLibraryDir（最棘手）**：
   - **不能在 LoadedApk 建立之前造假**（如在包解析阶段）。曾这么做，导致酷安的资源/split 解析 NPE，已回退。
   - **正确时机是 `makeApplication` 之后再改**：此时 LoadedApk 已用真实路径建好 ClassLoader 并缓存资源目录（mResDir），
     再改 `ApplicationInfo` 的字符串字段不影响资源/dex 加载。把 sourceDir/publicSourceDir 改成
     `/data/app/<pkg>-1/base.apk`、nativeLibraryDir 改成 `/data/app/<pkg>-1/lib/arm64`，split 置空。
   - **配套兜底重定向**：把这些干净的 apk/lib 路径重定向回真实文件，
     以防夜间模式/旋转重载资源、或按上报路径枚举 so 时又打开干净路径扑空。
   - `getPackageCodePath()`/`getPackageResourcePath()` 仍返回真实 mResDir（保证资源正确）；若将来遇到检这两项的壳再一并改。

4. **`/proc/self/{maps,smaps,mounts}`**：检测器读这些找宿主路径 / `libva++` / `/virtual/`。
   - 方案：在 native open/openat hook 里拦截对这些文件的打开，**读真实内容做行级过滤后写入匿名 `memfd`，返回该 fd**，
     使后续 `read()`/`mmap` 看到干净内容。
   - **过滤原则（关键）**：避免制造"连自己映射都没有"这种新特征——
     - 保留 app 自己的映射，但把含 `/virtual/` 的路径反向重定位成干净路径；
     - 丢弃 `libva++` 行、以及改写后仍含宿主包名的宿主/沙箱专属行；
     - mounts：丢弃含宿主包名 / `/virtual/` / `libva++` 的行。
   - 局限：只作用于**进程内打开**（memfd），不改磁盘；从设备外 `su` 读 `/proc` 仍是真实内容。只覆盖 self / 本进程 pid。

## 结果与边界

- 从基线 6 处泄露，逐阶段降到 vadetect **全部 0 泄露**（在 Mi10/A12/arm64、且被测 app 不做深度对抗时）。
- **边界很清楚**：这套只挡"读 `/proc`、读 `ApplicationInfo` 路径"这类**应用层**检测；
  挡不住原生反篡改（app 自己的 native 直接校验）、也挡不住从设备外读 `/proc`。

## 给 AppSandBox 的启示

- 反检测**顺序依赖** IO 重定向，IO 重定向依赖 arm64 hook——没有 hook 基座就不要碰路径级反检测。
- 改 `ApplicationInfo` 路径字段的**唯一安全时机**是资源/ClassLoader 建好之后（`makeApplication` 之后）。
- proc 过滤要"改写而非清空"，清空本身是新特征。
- 先建量化探针（如 vadetect），再谈隐藏，用泄露计数防回归。
