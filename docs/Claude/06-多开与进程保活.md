# 06 多开与进程保活（阶段 11、12）

## 多开机制（同一 app 多个 userId）

多开能力的骨架（VA 既有、本轮验证在现代机上仍可用）：

- **桩进程池**：lib 清单声明 `:p0`..`:p49` 共 50 组桩进程（StubActivity/CP/Service ×50）。
  服务端 `queryFreeStubProcessLocked` 为每个运行中的 guest 分配一个空闲 vpid，
  fork 后把进程改名为 guest 包名。不同 userId 跑在不同 OS 进程。
- **数据隔离**：每进程经 IO 重定向落到各自 `virtual/data/user/<id>/<pkg>`，互不共享（已实测 user 0 / user 1 各自独立填充）。
- **主页枚举**：`AppRepository.getVirtualApps` 枚举 `getInstalledUsers` → 为每个非 0 userId 显示独立图标。

**实测验证**：酷安 `CLONE` 后 `users=[0]` → `[0,1]`，两个实例可**同时**在 `ps` 看到两个 `com.coolapk.market` 主进程
及各自 `:xg_vip_service` 子进程，无崩溃、无 NSC 合并错误。

**ROM 行为注意**：MIUI 后台进程管理激进——顺序启动、把前一个切后台时，前一个实例可能被系统杀掉。
这是 ROM 行为不是多开缺陷；**快速连续启动**两个实例时二者可同时存活。

## 进程保活：前台服务 START_STICKY 重启（阶段 12）

**问题**：guest 的前台服务（START_STICKY）被杀后不重启。系统 AMS 只重启**真实包**，
沙箱的桩进程死后，服务端 `processDead` 只把 ServiceRecord 移除、从不重排重启。

**方案**（只对"前台的 started 服务"保活，最明确的"需常驻"信号）：

- `ServiceRecord` 记录 `userId / lastStartIntent / lastStartRealtime / restarts`；
  started 路径保存最后一次 start Intent。
- `processDead` 对满足 `foregroundId!=0 && lastStartIntent!=null` 的服务，
  延时重启（HandlerThread，延时 2s×次数），重投最后一次 Intent。
- **崩溃循环保护**：距上次启动 <30s 视为崩溃，`restarts++`；超过 4 次放弃；运行正常（>30s）后计数重置。
- 只重启前台 started 服务，避免误重启普通瞬时/非粘性后台服务。

**实测**：`su kill -9 <guest pid>` 后日志 `keepalive: restarted ...KeepAliveService (attempt 1)`，
服务在新进程重新 `onStartCommand`，仅一次重启、无循环。

## 已知次要缺口（记录备查）

- `getActiveNotifications` 读不回本 guest 已发的通知（沙箱把通知改挂宿主包 + 每应用 tag，
  形态 `pkg=<host> tag=<guestpkg>@<user>`）；`nm.notify` 本身成功、状态栏可见。属预期行为非缺陷。
- `JobScheduler.getPendingJob(id)` 返回 null（但 `getAllPendingJobs` 能列出）。
- **非前台**的 START_STICKY 后台服务被杀后不自动重启（仅前台服务保活）。
  现代 app 多依赖 JobScheduler/推送，影响有限。

## 给 AppSandBox 的启示

- 多开的本质是"桩进程池 + fork 改名 + per-进程路径重定向到各自 userId 目录"。
- 保活要**极度克制**：只保活最明确需常驻的信号（前台 started 服务），并强制崩溃循环保护，
  否则会把半初始化崩溃的进程反复拉起。
- 通知在沙箱里改挂宿主包是既有设计后果，`getActiveNotifications` 按原 id 读不回属正常。
