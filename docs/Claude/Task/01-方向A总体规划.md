# 01 方向 A 总体规划：真·多开/分身

日期：2026-09-30
目标：在 Google Play 上架一个分身类 App。用户可以对**已安装的真实 App** 创建一个或多个分身，每个分身数据相互隔离、可以长期稳定使用。

## 当前里程碑路线与治理（2026-10-01）

当前权威路线为：M2 Activity bootstrap；M3 ClassLoader/VPM；M4 Activity semantics；M5 Java storage；M6 Binder core；M7 Services；M8 Receiver/Provider；M9 Native；M10 Multi-process/WebView；M11 Virtual Location；M12 system compatibility；M13 compatibility matrix；M14 product/policy hardening。M2-M7 已关闭，M8-FIX 为 PARTIAL，M9 未开始。下方旧 M1-M7 草案仅保留历史背景，不再定义当前 milestone 编号或验收。

每个新 milestone 最多执行 `M<N>` 与一次 `M<N>-FIX`。FIX 仍不能达到原 PASS 标准时必须 `STOP / REVIEW ARCHITECTURE`，不得继续创建 `M<N>.2/.3/.4`，也不得降低验收标准。流程为 Planner/Reviewer → authoritative task → Execution session → RESULT + focused commits → Planner/Reviewer review → next milestone。

### Known Compatibility Risks

当前风险包括 native protected apps、custom linker/native loading、GMS/vendor dependencies、remote-process components，以及假定 physical package/UID/process 完全相等的 App。它们是待 M9/M10/M13 实证分类的风险，不预先宣布为不支持产品类别。Momo 的 native `.so` blocker 留在 M9；`com.reel` 系列若暴露身份等价依赖，必须记录具体 API 与行为。

## 一、选 A 之后先定的四件事

**1. 流程规则要改。**
`docs/CLEAN_ROOM.md`、`docs/design/27_NON_GOALS.md` 和每个 task 的"硬边界"都禁止 hook、hidden API 和 Binder 代理，这些规则不再适用。先写一份 ADR（`ADR-0013-DIRECTION-A`）把边界重新定清楚：

- **放开：** hidden API、系统服务代理、stub 组件、Instrumentation 和 ActivityThread 介入、arm64 native IO 重定向。
- **继续禁止：**
  - 复制 VirtualApp 等项目的源码（版权/专利角度仍需 clean-room 重写，`docs/Claude/01–09` 只作为问题与根因的输入）；
  - 反作弊绕过、Play Integrity/支付/银行类对抗；
  - 设备身份伪造。

**2. 分身对象改为"已安装的 App"，不再是"导入的 APK 文件"。**

- 这正是 Play 上分身类 App 能存活的前提：代码来自 Play 已安装的包，不属于"从外部来源加载可执行代码"。
- 用 `<queries>` 声明 MAIN/LAUNCHER intent 来列出可分身的 App，不申请 `QUERY_ALL_PACKAGES`。
- SAF 导入 APK 只保留在 debug 包里，作为开发工具。

**3. 专利风险需要单独确认。**
之前的 VirtualApp 项目因专利问题停止，而方向 A 基本是同一类技术路线。上架前应针对目标市场做一次专利检索（FTO）。这属于法律判断，技术规划给不了结论，但不应该跳过。

**4. 验收标准改成"真实 App 能跑"。**
不再用双设备矩阵加证据文档作为主要验收。每个里程碑的出口，是一份指定的真实 App 清单能完成指定操作。

## 二、现有代码怎么处理

| 模块 | 处理 |
|---|---|
| `GuestInstanceStore` / `GuestInstanceRegistry`（实例身份、隔离目录、原子写） | **保留**，作为分身实例（虚拟 userId）的注册表 |
| `GuestComponentResolver` / `GuestImplicitIntentResolver` | **保留**，作为虚拟 PMS 的 Intent 解析核心 |
| `:guest_runtime` 进程和 IPC 骨架、崩溃恢复 | **改造**，作为"虚拟系统服务"进程的雏形 |
| `GuestStore`（APK 复制和 SHA 校验） | 降级为 debug 工具；分身直接使用已安装 App 的 `sourceDir` |
| contract v1/v2、ActionSpec、逻辑 Activity carrier、逻辑 Service（Task-58） | **停止并移除**。Task-58 不提交；已提交的部分在 M1 删除 |
| `app/src/debug/.../experiments/*`（exp001–act009） | 归档或删除 |
| `docs/Claude/01–09` | 作为设计输入：记录问题和根因，按新架构重写，不照搬 |

## 三、目标架构（概要）

```text
宿主 UI 进程（App 列表 / 分身管理 / 快捷方式）
        │ IPC
虚拟系统服务进程（:vs）
  ├─ 虚拟 PMS：读取已安装包 → 改写 ApplicationInfo/PackageInfo（dataDir → 宿主私有）
  ├─ 虚拟 AMS：进程分配（stub 进程池）、Activity/Service/Provider 记录、任务栈映射
  └─ 实例注册表：虚拟 userId ↔ 数据根目录（复用 GuestInstanceStore）
        │
stub 进程池（:p0 … :pN，manifest 预声明）
  ├─ 进程启动：LoadedApk/ClassLoader/Resources → Application（模拟 bindApplication）
  ├─ 系统服务代理：IActivityTaskManager / IActivityManager / IPackageManager / 其他按需
  ├─ ActivityThread 介入：stub Activity → 还原真实 Activity/Intent
  ├─ Android 12+ AttributionSource / 包名校验修正
  └─ native IO 重定向（arm64 inline hook libc）
```

## 四、里程碑

每个里程碑大致对应一个执行 task，最多两个。

### M1：方向切换与底座（1 个 task）

- 写 ADR-0013；更新 CLEAN_ROOM、Non-goals；精简 `00_SESSION_REQUIREMENTS` 的证据和矩阵要求。
- 移除 contract 和逻辑组件相关代码与实验入口。
- 改 `applicationId`，配置 release 签名。
- 实现 hidden API 访问层，API31 和 API36 都要能用。
- manifest 预声明 stub 组件：多个 `:pN` 进程，每个进程配 stub Activity（覆盖 standard、singleTop/Task/Instance、各种 theme 变体）、stub Service 和 stub Provider。
- **出口：** release 包在 API31 和 API36 上能调用 hidden API；stub 进程能按需拉起。

详见 [M1-方向切换与底座.md](./M1-方向切换与底座.md)。

### M2：首个真实 App 启动闭环（核心，1–2 个 task）

- 虚拟 PMS：读取已安装 App 的 `PackageInfo`，生成改写后的 `ApplicationInfo`（`dataDir` 指向宿主私有目录）。
- 进程启动：在 stub 进程里建立 Guest 的 LoadedApk、ClassLoader 和 Resources，然后创建 Application，模拟 bindApplication。
- Activity 启动：代理 `IActivityTaskManager.startActivity`，把目标 Intent 换成 stub Activity；在 ClientTransaction 或 `mH` 回调里还原真实的 Activity 和 Intent。
- 处理 Android 12+ 的 `AttributionSource` 和包名校验（参见 `docs/Claude/03`）。
- **出口：** 1 个纯 Java 工具类 App（如计算器、记事本）能在分身中启动，页面跳转、返回和横竖屏旋转都正常。

### M3：多开与数据隔离（1 个 task）

- 虚拟 userId 和实例注册表对接：同一个 App 可以开多份，数据分开存放。
- Java 层路径改写：dataDir、SharedPreferences、数据库、缓存。
- arm64 native IO 重定向（inline hook libc 的 `open`、`openat`、`stat` 等），参见 `docs/Claude/02`。
- **出口：** 同一个 App 开 2 个分身，各自登录或写数据互不影响；删除一个分身不影响另一个。

### M4：组件全家桶（1–2 个 task）

- Service（start/bind，前台服务类型）、动态和静态 Receiver、ContentProvider（包括跨进程访问）、JobScheduler。
- 代理的系统服务要按参数类型定位参数，不能用固定下标，以应对各版本的接口漂移（参见 `docs/Claude/03`）。
- **出口：** 一个 AndroidX 应用、一个带 WebView 的 App、一个多进程 App 都能长时间稳定运行。

### M5：兼容性扩面（持续进行）

- 按兼容 Tier 2/3 建真实 App 回归清单：常见社交、工具、新闻类，外加 native `.so` 应用。
- 通知、推送、网络安全配置（NSC），参见 `docs/Claude/04`。
- 判断是否需要 32 位兼容插件；可以先只支持 arm64。
- GMS 方案单独评估：不支持 GMS 会让很多海外 App 用不了，但 MicroG 加签名伪造涉及 Play 政策，需要慎重决策（参见 `docs/Claude/07`）。
- 明确不支持加固和反沙箱的 App（参见 `docs/Claude/08`）。

### M6：产品化（可以从 M2 起并行）

- 首页：可分身 App 列表；添加分身；每个分身可自定义名称和图标角标；支持创建桌面快捷方式。
- 进程管理：保活策略、一键清理、崩溃提示（参见 `docs/Claude/06`）。
- UI 按 `docs/Codex/UI-PLAN.md` 和 `docs/Claude/09` 实施，支持中英文，适配深色模式。

### M7：上架准备（1 个 task）

- 隐私政策、Data Safety 表单、前台服务类型声明、target API 合规。
- 对照 Play 政策逐条自查：Device and Network Abuse，以及禁止帮助绕过其他 App 的安全机制。
- 用 Play Console 内测轨道试跑；兼容性说明中明确写出不支持的 App 类型。

## 五、需要改的工作方式

- **每个 task 的出口是"哪些真实 App 做到了哪一步"。** 结果文档控制在 20 行左右；双设备验证保留，但不再为每项验证写证据文档。
- **测试重心转移。** 风险测试集中在虚拟 PMS/AMS 的状态、进程死亡恢复和路径重定向上，这些才是方向 A 真正的高风险点。原子写这类加固已经够用了。
- **测试设备不变：** API31 真机 `7b670025`，API36 模拟器 `emulator-5554`。

## 六、主要风险

| 风险 | 影响 | 应对 |
|---|---|---|
| 专利 | 可能无法上架或被迫下架 | M7 前完成 FTO；技术实现保持独立设计 |
| Play 政策 | 审核拒绝 | 只分身已安装 App；release 不执行外部 APK 代码；不申请 `QUERY_ALL_PACKAGES` |
| hidden API 随版本收紧 | 新 Android 版本失效 | 访问层集中封装，按 API 分支，M1 起在 API36 验证 |
| 系统服务接口漂移 | 代理失效、崩溃 | 按参数类型定位，每个版本做回归 |
| 加固和反沙箱 App | 个别 App 无法运行 | 列入不支持清单，不做一对一对抗 |
