## 2. 关键问题：只能运行专门适配过的 Guest

所有能力的前提是：Guest APK 的 manifest 里必须写 AppSandbox 专用的 meta-data（`com.example.appsandbox.guest.CONTRACT_VERSION`、`ACTION_SPEC`、`SERVICE_SPEC` 等，见 `test-guests/GuestTestApp/src/main/AndroidManifest.xml`）。

结果是：**用户导入任何一个真实 App，都只会看到 "Unsupported Guest"。** 现在唯一能跑的是项目自己的 GuestTestApp。

这由项目自己定下的边界决定（clean-room 规则、Non-goals，每个 task 都禁止 `attach`、hidden API、Binder 拦截和 hook）。在这些约束下，运行任意第三方 APK 在技术上做不到，`docs/review/12_HARD_LIMITS.md` 已经写明。

## 3. 是否偏离目标：是

1. **会话规则里写的目标没有兑现。** `docs/Codex/00_SESSION_REQUIREMENTS.md` 第 8 节的第一优先级是"尽快形成可运行的简单多开或虚拟化演示闭环"。但最近 20 多个 task 的实际产出，是给一个计数器 Demo 加固持久化和 IPC，再做双设备矩阵验证。
2. **里程碑名称和实际内容对不上。** Roadmap 上 M6 叫 "Activity subset"，M7 叫 "Services"。实际交付的是"声明式逻辑 Activity/Service"，与 Android 的 Activity/Service 语义没有关系，也不可能演化成对真实 App 的兼容。
3. **投入重心放在验证流程上。** 原子写、tombstone、request ledger、2048 条历史上限这类加固，对没人用的计数器 Demo 来说投入产出比很低。

## 4. 是否有效推进

- **可以复用的部分（有效）：** 导入和存储（GuestStore）、实例注册表（InstanceStore）、组件解析器、独立进程和 IPC 骨架。
- **很可能是死路的部分：** contract v1/v2、ActionSpec、逻辑 Activity carrier、逻辑 Service。这些是"插件协议"，真实 App 永远不会实现它们。
- **上架必需但完全没做的：**
  - `applicationId` 还是 `com.example.appsandbox`，Play 会拒绝 `com.example` 前缀。
  - 没有签名配置，没有应用图标（manifest 里没有 `android:icon`）。
  - 界面是代码里动态生成的原始按钮（例如 "Select 3fa2b1c9"），文案都是硬编码英文，没有做多语言。
  - 没有隐私政策，没有 Data Safety 表单相关准备。
- **Play 政策风险：** release 包会对用户导入的 APK 调用 `DexClassLoader`（`GuestWorkspaceActivity.kt:378`、`GuestActivityCarrierActivity.kt:160`）。Play 的 Device and Network Abuse 政策禁止从 Play 以外的来源加载可执行代码。"导入外部 APK 并执行"是比"分身已安装的 App"风险高得多的形态。`docs/design/22_PRODUCT_AND_PLAY_CONSTRAINTS.md` 把这一点标成了 `RESEARCH NEEDED`，但一直没有去研究。

| 选项 | 说明 | 结论 |
|---|---|---|
| A. 真·多开/分身 | 放弃现有 clean-room 和无 hook 边界，走 stub 组件加系统服务代理路线；专利、Play 政策风险和兼容对抗成本最高 | **用户选定（2026-09-30）** |
