# AppSandbox 会话协作要求

> **状态：已作废（2026-09-30）。** 仅作历史参考，不再约束任何会话。
> 当前规则见仓库根目录 [AGENTS.md](../../AGENTS.md)，目标与任务见 [docs/Claude/Task/](../Claude/Task/README.md)。

更新日期：2026-09-26
原状态：所有后续 Codex/ChatGPT 项目会话和 task 的必读规则。

## 1. 每次会话开始必须读取

按以下顺序建立上下文：

1. 本文件：docs/Codex/00_SESSION_REQUIREMENTS.md
2. git status --short --branch
3. git log -5 --oneline
4. 最新一个已完成的 docs/experiments/TASK-*-RESULT.md
5. 当前相关的 docs/design/、ADR 和实验结果
6. 当前 task 文件

不要每次重新通读全部历史 task。只有遇到依赖或结论冲突时才回溯旧文档。

## 2. 一个 task 必须完成一个大目标

禁止再为单次设备验证、单个文档修正、一个脚本修复、一个 API 补测、一次简单重试或仅确认工作区状态分别创建 task。

一个 task 应覆盖一个完整里程碑：

研究/预检 -> 实现或实验 -> API31/API36 验证 -> 自行修复 -> 回归测试 -> 必要记录 -> focused commit

除非存在真正阻塞，同一会话必须连续完成这些子目标，不能每几分钟停下来等待用户重新布置。

## 3. Task 文件必须短而面向目标

新的 task 文件优先控制在约 80～150 行，避免重复粘贴全部项目历史和相同禁令。

标准结构：

- 大目标
- 当前基线
- 验收标准
- 允许范围与硬边界
- 小目标和执行顺序
- 测试矩阵
- 提交要求
- 最终只需回传的关键信息

已经写入本文件的通用流程不要在每个 task 中全文重复。

## 4. 执行会话的自主权

执行会话应自行完成：

- 阅读代码和文档
- 选择符合现有架构的实现方式
- 修改被授权范围内的文件
- 启动或恢复 API31/API36 设备
- 运行构建、测试、脚本和回归
- 修复本轮发现的普通缺陷
- 更新必要的结果文档
- 创建 focused commit
- 保持不 push，除非用户明确要求

以下情况不需要中途询问用户：可自行恢复的构建失败、模拟器安全重试、小范围脚本或报告问题、同一大目标内的测试补充，以及不改变架构边界的实现调整。

## 5. 只有这些情况可以提前结束

- 需要用户提供外部账号、密钥、设备或不可获取的文件
- 同一技术阻塞经过合理的多次尝试仍无法突破
- 继续操作会越过当前明确禁止的安全或架构边界
- 用户现有改动与任务目标直接冲突且无法安全合并
- 需要用户在两个影响重大的产品方向之间决策

设备暂时离线不是立即结束理由。应先尝试恢复、诊断和复用已有脚本。

## 6. 审视会话的职责

1. 核对代码、证据、结果文档、Git 状态和提交。
2. 直接指出真实问题，不为措辞或非关键差异创建独立 task。
3. 可在下一大目标中修复的小问题，合并进下一 task。
4. 不再为每个实验阶段创建一份超长提示词。
5. 每次只创建一个覆盖完整里程碑的下一 task。
6. 最终回复保持简短：审视结论、关键风险、下一大目标和 task 路径。

如果上一任务已经完成，应推进到下一个有产品价值的里程碑，而不是反复补写总结。

## 7. 实现、测试、文档的优先级

实现类 task 的工作优先级必须是：

1. 真实产品代码和关键架构能力
2. 覆盖高风险行为的自动化测试
3. 可重复运行的验证脚本
4. 最小结论文档
5. 原始证据，仅在确有长期复核价值时保留

不得用大量文档、日志、dump、截图或字段回显代替核心实现和风险测试。实现类提交中，production/debug 源码、测试和脚本应构成主要增量；tracked 文档与 evidence 默认不得超过源码、测试和脚本新增量，理想情况下控制在其 20% 以内。

结果文档通常不超过 80 行，只记录决策、通过/失败结论、关键版本事实和已知限制。架构决策或兼容性边界确有变化时才新增 ADR/研究文档。

会话最终回传只包含：状态、完成的大目标、关键验证、未完成或风险、提交、下一阶段是否可开始。

## 7A. 风险驱动测试是完成条件

执行会话在编码前应识别本轮最危险的状态变化和失败点，测试投入按风险排序，不按类或字段数量排序。

以下测试不能作为核心验收：只验证 data class getter、构造后字段未丢、常量值、无分支序列化 happy path，或只证明测试对象能够被创建。

涉及持久化、实例身份或路径的代码，必须按适用范围覆盖：

- 原子写中途失败后旧状态仍可读取
- 主文件损坏、备份恢复和双重损坏 fail closed
- 路径逃逸、符号链接或伪造 dataRoot 被拒绝
- 并发 create/delete、重复 instanceId 和多 Store 实例竞争
- registry 成功但目录操作失败，或目录成功但 registry 提交失败时的回滚
- 删除一个实例不会删除 Guest revision 或其他实例
- 进程重启和 schema 迁移/未知版本行为

难以触发的错误必须通过依赖注入、文件后端抽象、failure point 或等价可控方式测试。不能因为真机 happy path 通过就跳过故障测试。

每个 task 的验收标准应明确“哪些危险分支被测试”，而不是笼统写“补单元测试”。发现核心代码不可测试时，应先做最小可测试性重构，再继续堆叠功能。

## 7B. 证据只保留结论，不默认入库原始输出

API31/API36 验证仍必须真实执行，但默认只把精简结论写入结果文档。以下内容默认不提交 Git：

- 完整 `dumpsys`、`logcat`、bugreport 或命令回显
- 每台设备重复的大段状态文件
- 截图、录屏和其他二进制运行证据
- 可由脚本重新生成的 APK hash 清单、临时报告和中间输出

验证脚本应把原始输出写到 `build/reports/`、临时目录或其他已忽略路径，并通过断言和退出码表达成功/失败。只有出现平台差异、回归、不可重复故障或安全边界争议时，才提交最小相关片段，并在结果文档解释保留原因。

双设备结果不要复制两份相同背景；每台设备只保留 API、设备标识、关键断言和最终结论。脚本本身和自动化测试是首选的可复核证据。

## 8. 进度优先级

1. 尽快形成可运行的简单多开或虚拟化演示闭环
2. Activity carrier 和 Guest 页面运行能力
3. API31/API36 可重复验证
4. 数据隔离、多实例和失败恢复
5. 再扩展兼容性、服务、广播、Provider 和复杂 APK

研究必须服务于下一步实现。除非安全边界或 Android 内部机制确实未明确，不要连续进行多个纯文档 task。

## 9. 阶段闸门不是微任务闸门

Research -> Experiment -> Decision -> Implementation -> Integration 仍然有效，但可以在一个大 task 内完成多个相邻环节。

例如，一个 task 可以完成 P0 可达性观察、根据结果选择 adapter、完成不跨 attach 边界的 P1 原型、API31/API36 验证和 fail-closed 回退，前提是 task 已明确授权该范围。

涉及以下高风险边界时仍需单独审视后授权：

- Activity.attach
- Guest 生命周期正式接入
- ActivityThread/ClientTransaction 行为修改
- Binder/ServiceManager interception
- Hook/Xposed/native 注入
- production runtime 大范围修改

## 10. Git 与证据

- 每个大目标使用一个或少量 focused commits。
- 不 push，除非用户明确要求。
- 不提交 AVD userdata、构建产物、cache、临时 APK、完整 dump、截图或无关日志。
- 原始设备输出默认写入 Git 忽略的 `build/reports/`，不写入 `docs/experiments/evidence/`。
- 提交前运行 `git diff --stat` 和 `git diff --numstat`，确认实现与高风险测试是主要改动；若文档/evidence 接近或超过代码/测试，必须先删减或说明不可替代原因。
- 对新增或修改的高风险 production 逻辑，缺少行为测试时不得提交为完成。
- 未经当前 task 明确授权，不修改历史 evidence；允许按本文件规则删除超量、可重建的 dump/截图，同时保留结果结论。
- 工作区有无关用户改动时保留并避开。
- task 输入文件默认不和实现提交混合。

## 11. 后续 task 的默认目标大小

后续 task 至少应包含以下规模之一：

- 一个可运行的端到端实验里程碑
- 一个生产子系统的完整最小实现
- 一个组件兼容等级的双版本闭环
- 一个可演示的产品能力
- 一个高风险边界的完整预检加安全原型

仅写设计、补一台设备结果或修一处报告路径，通常不再作为独立大目标。

## 12. 当前流程变更

历史 task-18 至 task-27 保留；后续可以删除其中不再需要的超量原始 dump、截图和可重建 evidence，但保留结果文档与结论，不伪造或改写历史结果。

从下一份 task 开始：

- 必须在开头要求读取本文件。
- task 必须定义一个大目标。
- task 内包含小目标和步骤。
- 执行会话必须完成整个大目标才结束。
- 审视会话不再用大量篇幅重复已有背景。
- 实现类 task 必须明确高风险测试清单和 evidence 预算。
- 原始设备输出默认不进入 Git；结果文档只保留精简结论。
