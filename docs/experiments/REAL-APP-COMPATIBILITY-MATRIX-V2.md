## Round 13 System Service Mediation

API31 runtime probes proved `ConnectivityManager` is obtained by `SystemServiceRegistry` from the `connectivity` Binder, but its wrapper cache is application-context scoped: configuration, package, and device-protected derived Contexts still returned the Host-cached manager. Candidate A therefore cannot create a Guest-only manager without the already-rejected hidden constructor/field path. Candidate B's process-wide pre-wrapper Binder replacement and Candidate C's existing M6 interface proxy can identify the active M10 Guest generation, but cannot distinguish a Host Context call from a Guest Context call inside that physical slot; applying Guest manifest policy there would alter Host behavior. All three candidates were rejected and `SELECTED_SYSTEM_SERVICE_MEDIATION=NONE`; no production runtime or Host manifest permission was retained.

QQ Browser and Baidu still declare and hold Guest `ACCESS_NETWORK_STATE`, while the installed Host remains without it, so both remain at their previous first blocker. The conditional 18-App/API36 matrix was not rerun because production runtime did not change; counts remain API31 `4/18` and API36 eligible `2/3`. Momo and SuperList stayed first-frame PASS for I0/I1 on API31 and API36; Termux API36 I0/I1 retained Receiver translation `flags 0 -> 2`. ### Activity task/process model and remaining context contracts

Activity launches were the last shared blocker for Apps that start but never show their second screen. (1) All Guest Activities of one launch mode shared one stub class per slot, so the system treated an unrelated Guest `singleTop`/`singleTask` Activity as the reuse target (`START_DELIVERED_TO_TOP`, wrong bring-to-front: DingTalk, Baidu). (2) Stub Activities had no `taskAffinity`, so a Guest launched into the Host's task and `isTaskRoot()` splash checks finished themselves (Baidu); each slot now has its own affinity, so a clone is the root of its own task. (4) `LoadedApk.makeApplication`'s context-class-loader contract is reproduced, and routed Service intents unparcel Guest extras with the Guest loader (Baidu `:loki`). ### Guest Application on a framework ContextImpl (Frida-assisted)

Frida spawn-gating on the stub process showed Lark's `InitAutoInitModuleTask` reading `Application.mBase.mPackageInfo.mClassLoader` and replacing it with its `ModuleAutoInitClassLoader` (the LoadedApk class-loader hook also used by hotfix/plugin frameworks). The Guest Application's base was the `GuestContext` wrapper, which has no `mPackageInfo`, so module auto-init failed silently and `MainActivity.<clinit>` read a null DI holder. The Guest Application now attaches to `ContextImpl.createAppContext(activityThread, guestLoadedApk)`, whose `ApplicationInfo` already points data/device-protected directories at the instance (ZeroAdapt I0/I1 data probes stay under their own instance roots on API36), with `GuestContext` as fallback. `GuestInstrumentation` instantiates Applications and Activities through the Guest `LoadedApk`'s current `mClassLoader`, so App-installed class-loader wrappers take effect. `ApplicationInfo.processName` now keeps the Guest's default process (iQIYI's `QyContext.isMainProcess` compares it with the logical process name), while stub `ActivityInfo.processName` stays physical. ### App-specific external storage, process identity, and per-component cross-process routing

A second-pass classification of the last sweep's SecurityExceptions and crashes found six generic boundaries, each fixed against the platform contract. (1) A Guest's `Android/{data,obb,media}/<guest>` dirs were outside the Host UID (`Failed to ensure ... does not belong to 10293`: iQIYI, Douyin Lite, Duokan, Kuaixun, Qunar, DingTalk, WeChat). `Environment.sCurrentUser` is replaced by a `UserEnvironment` subclass (new `hidden-bridge` module, compiled against a never-packaged stub) that maps only the Guest package to `<volume>/Android/<kind>/<host>/virtual/<instance>`; every ContextImpl therefore gets Host-owned per-instance dirs, and the native IO layer maps self-assembled logical paths (`/sdcard`, `/storage/self/primary`, each volume) to the same roots. Instance deletion removes them. Overriding hidden methods needs a real hidden-API exemption: reflection on `setHiddenApiExemptions` is itself blocked since API 30 (it had been failing silently), so the exemption list is now installed from a freshly attached native thread, which ART treats as a trusted caller. (2) `/proc/self/cmdline` returned the physical stub name, so SDKs deciding main vs. sub-process took the wrong branch (Baidu helios recursed into its own IPC provider: `StackOverflowError`); `open*` of the process's own cmdline now returns a memfd with the logical name, while Host code uses the name captured before virtualization. (3) Package-checking services that every Guest ContextImpl reaches through `ServiceManager` get the physical-package facade: `appops` (AppOpsAdapter only covered the Host context's manager), `uri_grants` (Baidu crash), `mount` (API 30+ creates external cache dirs only via `StorageManager.mkdirs`), `telephony.registry` (WeChat crash in all processes), `clipboard`, `netstats`, `appwidget` (iQIYI crash), `role` (QQ Browser crash); the new ones are optional so a ROM without the service still launches. (4) A receiver delivered to a process already running the Guest unbound its Application, and `handleReceiver` created a second one (Baidu `ClockWidgetProvider`: "main activity lifecycle has already been initialized"); an Application on a framework ContextImpl now stays bound. (5) Provider, Service and receiver routes compared the target process with the package name instead of the current logical process, so a sub-process asking for a main-process provider fell through to the system (QQ Browser `:block` `Permission Denial ... not exported`); once routed, the coordinator did not know the Activity-started main process and started a second copy of it. The entry process now registers with the coordinator (its agent Messenger runs on a worker thread and doubles as the death token), so routes reuse it. (6) A running process answered every later provider authority with the binder of the authority that started it, and every Service of a remote process shared stub index 0, so AMS handed WeChat `:push` the binder of whichever Service bound first (`Binder invocation to an incorrect interface`). The coordinator now asks the target process's agent to publish each further authority and to allocate each Service its own stub; once the Guest runtime exists this runs off the main thread (QQ Browser's main thread waits on `:block` while `:block` asks for a main-process provider).

API31 dual-instance first frame is now `25/31`: Arrow, Baidu, Coolapk, Damai, Damai Helper, Detector, DingTalk, Dragon Read, Duokan, Hide App List, iQIYI, Incy, Kuaixun, Kugou Lite, Lark, Momo, MusicPlayGo, Network Toolbox, PDF Editor, QQ Browser, Qunar, Sudoku, SuperList, WeChat, Zhihu, with no FATAL in the final recheck of the previously crashing ones. ### Stub Service pool

Each slot had four stub Services and a Guest Service kept its stub forever, so WeChat filled slots p0 and p2 (4/4 each) within 25 s and any further Service of those processes failed with `no StubService available`. Every Guest Service still needs its own stub component (one real AMS ServiceRecord per Guest Service keeps start/bind/foreground/`stopSelf(startId)` semantics with the framework), so the pool grows instead: `scripts/gen-stub-services.sh` generates 32 stub Services per slot (classes + manifest entries). A Guest Service keeps its stub across destroy and restart (a start racing the framework's `STOP_SERVICE` still finds its mapping); a destroyed Service's stub is reclaimed only when the pool has no never-used index, oldest destroy first. `stopService` for a local Guest Service that holds no live stub answers 0 instead of allocating one. Index 0 (`P<slot>Service`) is excluded: GuestRuntimeService starts it as the slot's keep-alive, so a Guest bound to it reached the already-running stub and never connected (API36 I1 `S0 -> null`), leaving 31 per slot. The R15 fixture now declares 40 main-process and 8 `:remote` Services whose binders answer with their own class name; it binds 20+8, unbinds, then binds 20 more (40 distinct main-process Services, 9 on reclaimed stubs): API31 and API36, I0 and I1, wave 1 `28/28` and wave 2 `20/20` own binders, none refused. WeChat, QQ Browser, Baidu, iQIYI, Kugou Lite, DingTalk and Momo pass I0/I1 first frame with no FATAL, no `incorrect interface` and no pool exhaustion; API36 Momo and Network Toolbox pass. Evidence: `build/reports/m15/api31t`, `api36t`, `sweep-s17.txt`.
