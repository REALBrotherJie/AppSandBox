GuestTestApp 没有 native 代码，x86_64 模拟器可以直接运行。

## 审计 2：两项分类错误

task-14 把以下两项分类为 `LOADEDAPK_SENSITIVE`：

* `LayoutInflater.context` = Host Application / Host Activity
* `createConfigurationContext()` = Host ContextImpl / Host package

但 `Exp003aControlledContext` **没有重写** `getSystemService()` 和 `createConfigurationContext()`。这两个调用经过 `ContextWrapper` 直接委托给了 base，结果自然是 Host。

它们是 **Controlled Context 的委托缺口**，不是 LoadedApk 的证据。

新增分类：

```text
C0_DELEGATION_GAP   Controlled Context 未重写，委托给 Host base 导致；可用 PUBLIC API 修复
```

EXP-003B0-P-RESULT.md 中这两行改为 `C0_DELEGATION_GAP`，并注明本审计。

## 审计 3：getApplicationContext() 语义错误

当前实现：

```kotlin
override fun getApplicationContext(): Context = this
```

B0-P 结果中 `applicationContext === this 为 false，返回 Controlled Context`，被归为 `BASE_CONTEXT_DOMINANT`（正确）。

**这在语义上是错的。** 真实应用普遍这样写：

```java
MyApp app = (MyApp) context.getApplicationContext();
```

按现有实现会抛 ClassCastException。

正确语义：Guest Application 创建（attach）之后，Guest 侧所有 Context 的 `getApplicationContext()` 都应返回 **Guest Application 实例**。

## 审计 4：hidden observation 仍然不需要

B0-P 中被认为「Host 敏感」的几项，经审计 2、3 都属于包装层问题，可以用 PUBLIC API 修复。目前 **没有** 只能通过读取框架内部字段才能回答的问题。

决定：

```text
Hidden observation request = NOT NEEDED NOW
在 WS-2 完成后，如果仍有无法用 PUBLIC 方式解释的 Host 行为，再单独申请
```

task-11/12/13 合并成了一个 checkpoint 提交（9e96c99），没有按 task 分组。接受，不回退。本轮开始按工作流分别提交。

# 二、全局规则（所有工作流适用）

# 五、WS-2：Controlled Context C1（PUBLIC-ONLY）

目标：把 C0 升级为 C1，修复审计 2、3 暴露的缺口，并补齐存储相关接口。

新建：

```text
exp003c1/Exp003c1ControlledContext.kt
```

**不要修改** `exp003a/Exp003aControlledContext.kt`（保留 C0 作为基线对照）。

## 5.1 base Context

固定使用：

```text
base = Host applicationContext
```

（task-14 D3 的结论。Activity 底座不再使用。）

## 5.2 必须实现的行为

### A. Application 绑定

* 新增 `bindApplication(app: Application)`
* 绑定前：`getApplicationContext()` 返回自身（与 C0 一致）
* 绑定后：`getApplicationContext()` 返回 **Guest Application 实例**
* 所有由 C1 派生出来的 Context，`getApplicationContext()` 也返回同一个 Guest Application

### B. LayoutInflater

* `getSystemService(LAYOUT_INFLATER_SERVICE)` 返回：

```kotlin
LayoutInflater.from(baseContext).cloneInContext(this)
```

* 在 C1 实例内缓存，保证同一个 C1 多次获取得到同一个对象
* 其他 `getSystemService(name)`：**不改变行为**，委托给 base，但要记录每个被请求的服务名（用于后续的系统服务清单）

### C. Theme

* `getTheme()`：基于 Guest Resources 的 `newTheme()`
* 默认主题：`guestInfo.theme`；如果为 0，使用一个框架默认主题（如 `android.R.style.Theme_DeviceDefault_Light`），并记录用的是哪一个
* `setTheme(resId)`：应用到 Guest 的 Theme 上

### D. 派生 Context

| 方法 | C1 行为 |
|---|---|
| `createConfigurationContext(config)` | 返回新的 C1 实例，其 Resources 来自 `getResourcesForApplication(guestInfo, config)`（ADR-0007 的 API 31 重载） |
| `createDeviceProtectedStorageContext()` | 返回新的 C1 实例，数据根目录为 **instance 的 device-protected 根目录**（位于 Host 的 device-protected 存储下，按 instance 划分） |
| `createAttributionContext(tag)`（API 30+） | 返回新的 C1 实例，保留 Guest 语义；`AttributionSource` 仍是 Host（ADR-0002），记录 tag 是否保留 |
| `createPackageContext(guestPkg, …)` | 不改变，预期 NameNotFoundException，记录 |
| `createDisplayContext` / `createWindowContext` | 不实现，记录为 DEFERRED |

所有派生出的 C1 都必须满足：包名、ClassLoader、Resources、存储路径全部是 Guest 的。

### E. SharedPreferences

先观测，再实现：

1. **观测**：用 C0 调用 `getSharedPreferences("exp003c1", MODE_PRIVATE)` 写入一个 marker，记录文件落在哪里（预期落在 Host 的 `shared_prefs`，属于泄漏）
2. **实现**：C1 重写 `getSharedPreferences(name, mode)`，返回一个 **实验用** 的 `SharedPreferences` 接口实现：
   * 存储在 `instanceRoot/shared_prefs/<name>.xml`（格式可以简化，但要能跨进程重启读回）
   * 同一个 C1 内，同名返回同一个实例
   * 支持 `edit/putString/putInt/putBoolean/putLong/putFloat/putStringSet/remove/clear/apply/commit`，以及 `OnSharedPreferenceChangeListener`
   * 不追求与框架实现完全一致；已知差异写进结果文档
3. 同时重写 `deleteSharedPreferences(name)`

这是 **debug 实验代码**，不是生产实现。

### F. 数据库

C1 重写：

* `getDatabasePath(name)` → `instanceRoot/databases/<name>`
* `openOrCreateDatabase(...)`（全部重载）→ `SQLiteDatabase.openOrCreateDatabase(File, ...)`
* `deleteDatabase(name)`、`databaseList()`

用标准 `SQLiteOpenHelper(context=C1, ...)` 建库、建表、读写一行，验证文件落在 instance 目录。

### G. 外部存储

`getExternalFilesDir(type)`、`getExternalCacheDir()`、`getObbDir()`：

* 路由到 Host 对应外部目录下的 `sandbox/<instanceId>/...` 子目录
* 记录 Host 原始路径与路由后的路径

### H. 明确不处理的接口（只观测并分类）

以下调用 **不做任何修改**，只观测结果并分类为 `HOST_IDENTITY_REALITY` / `UNSUPPORTED` / `DEFERRED`：

* `getContentResolver()`
* `registerReceiver(...)`（注册一个无害的自定义 action 后立即注销）
* `sendBroadcast(...)`（发送一个只有本进程接收的自定义 action）
* `startActivity(...)`、`startService(...)`、`bindService(...)`：**不调用**，只记录为 UNSUPPORTED（组件阶段处理）
* `checkSelfPermission(...)`：记录返回的是 Host 的授权状态
* `getPackageManager()`：Guest 包查询预期 NameNotFoundException

## 5.3 C1 验证矩阵

对 C1 本身及其每一种派生 Context，逐项检查：

```text
packageName / classLoader / resources / assets / applicationInfo
filesDir / cacheDir / codeCacheDir / noBackupFilesDir / dataDir / getDir
getDatabasePath / SharedPreferences 文件位置 / externalFilesDir
getApplicationContext（绑定前 / 绑定后）
LayoutInflater.context
theme（能否解析一个 Guest 主题属性）
```

每项：PASS / FAIL / 分类。

## 5.4 负面对照

* Host 的 `shared_prefs` 目录中 **不能** 出现 C1 写入的 marker
* Host 的 `databases` 目录中 **不能** 出现 C1 创建的库
* Host 的 LayoutInflater（`LayoutInflater.from(hostActivity)`）的 context 仍是 Host
* Host 的 Theme 不受影响
