# 一、本轮两个核心纠偏点

## Correction 1 — EXP-002 Option A 无效

之前 Option A 使用：

Resources(
Resources.getSystem().assets,
...
).apply {
addLoaders(loader)
}

之前把它认为：

“System-only AssetManager + Guest loader = isolated Guest Resources”

这个结论撤销。

原因：

Resources.addLoaders() 会更新 Resources 底层 AssetManager 的 loader 集合。

而：

Resources.getSystem().assets

来自进程共享的 System AssetManager。

因此：

Option A 会修改共享 AssetManager 状态。

它不是一个独立 Guest AssetManager。

不能作为 Guest resource isolation architecture。

---

## Correction 2 — EXP-003 Application.attach 风险

当前设计准备：

Controlled Context
→ Instrumentation.newApplication()
→ Guest Application

但 Android Application.attach() 内部会获取：

ContextImpl.getImpl(context)

而 ContextImpl.getImpl() 会剥开 ContextWrapper。

如果：

ControlledGuestContext
↓
Host ContextWrapper
↓
Host ContextImpl

那么最终 Guest Application 可能获得：

Host LoadedApk / Host package runtime state。

因此：

Instrumentation.newApplication()

现在不能继续被视为“只要 Controlled Context getter 正确就安全”。

必须先研究：

Application.attach
ContextImpl.getImpl
LoadedApk

之间的关系。
