# 四、建立“关键假设清单”

创建：

`docs/review/02_CRITICAL_ASSUMPTIONS.md`

进行排序。

至少分析以下假设：

---

## A1：未安装 APK 可以仅依赖 Host 进程完成代码加载

问题：

我们是否能够在不向 PMS 安装 Guest 的情况下：

* 创建 ClassLoader
* 加载 Guest classes
* 加载 Guest native libs

状态：

需要证据。

---

## A2：Guest Resources 可以独立于系统安装状态创建

需要确认：

未安装 APK 是否能够构造：

* AssetManager
* Resources
* Resources.Theme
* Configuration

并保证：

Guest `R.xxx` 正确工作。

---

## A3：Guest Application 可以在 Host 进程中被正确创建

需要确认：

是否能够构造：

* Guest ClassLoader
* Guest Resources
* Guest Context

然后调用：

Application.attach / onCreate

且不会依赖 PMS 已安装状态。

---

## A4：Guest Activity 可以在系统不知道 Guest package 的情况下运行

这是最关键假设之一。

必须拆开两个问题：

### A4.1

Java Activity 对象能否在 Host 进程中手动创建？

### A4.2

即使可以创建：

能否获得真正 Android Activity 所需要的：

* Window
* token
* task
* lifecycle
* saved state
* configuration
* result delivery

这两个问题不能混为一谈。

---

## A5：Android 系统可以管理 Host Component，而我们映射 Guest Component

这是目前 Activity Runtime 潜在核心方向。

但本轮不能假设成立。

必须明确需要验证：

```text
System:
只认识 Host

Runtime:
认识 Guest

Host system component
↔
Guest logical component
```

这种两层模型是否能够保持：

Activity lifecycle

Task

Result

Configuration

Window

等行为。

---

## A6：Guest Context 可以独立存在

研究：

ContextImpl

ContextWrapper

Application Context

Activity Context

Service Context

Package Context

必须判断：

我们是否能够可靠构造：

Guest Context

还是最终必须依赖某个 Host Context 并做代理。

---

## A7：PackageManager 行为可以由局部 compatibility layer 补齐

需要验证：

Guest App 对 PackageManager 的调用到底有多少种来源。

例如：

```text
Context.getPackageManager()

直接 Binder

framework internal

library internal
```

如果只代理 `Context.getPackageManager()`：

是否足够？

大概率不是。

但必须基于 Android 机制分析。

---

## A8：Guest packageName 可以作为逻辑身份存在

需要区分：

Java 层看到的 packageName

Binder caller package

Linux UID

AppOps attribution

system_server package validation

这些不能混在一起。

---

## A9：多实例可以共享 APK/Dex/Resources

但：

Data

Application

Class static state

Native state

是否必须隔离？

尤其：

两个相同 packageName Guest instance
运行在同一个进程

是否真的能做到强隔离？

需要提前分析。

---

## A10：单进程模型是否可行

如果两个 Guest 同时运行：

* static variables
* singleton
* native globals
* System properties
* ThreadLocal
* process-level state

会发生什么？

这可能直接决定：

Multi-instance 是否必须多进程。

# 二十四、这轮的核心思想

从现在开始：

不要把“Virtual App”看成一个大功能。

把它拆成一系列能够独立证伪的假设。

我们的目标不是证明：

“这个方案肯定可行”。

而是尽可能早地发现：

“哪个假设不成立”。

越早发现架构错误：

代价越低。

因此整个项目后续固定采用：

```text
Question
↓
Android/AOSP Research
↓
Hypothesis
↓
Minimal Experiment
↓
Observed Result
↓
ADR
↓
Production Implementation
```

禁止：

```text
猜一个方案
↓
写几千行代码
↓
发现 Android 不允许
↓
全部重写
```

本轮完成文档后停止。
